# 墨读 · 书源引擎 M5

Legado 书源兼容的自研阅读 App。**M1 目标：书源引擎全链路跑通**（搜索 → 详情 → 目录 → 正文）；**M2 目标：阅读体验补齐**——书架完善、章节缓存、正文净化、TTS 朗读；**M3 目标：本地书籍导入 + 全端风格统一**——TXT/EPUB 导入书架、移动端底部导航、卡片化书源管理、排版面板；**M4 目标：分页阅读 + 排版面板扩充**；**M5 目标：大改版（纸墨视觉）+ 阅读功能极大加强**。

> 仅限个人自用：请勿传播书源、勿用于营利。书源内容来自第三方网站，与本软件无关。

## 运行

```bash
npm start                # 启动 dev server → http://127.0.0.1:8080
```

浏览器打开后：**书源管理 → 载入示例书源**（内置 2 个公版/练习源），即可去「搜书」体验；
也可以在**书架 → 本地导入**直接读手机里的 TXT / EPUB。

## v0.6.1 修复（功能可用性 · 返回栈 · 导出）

> 针对实机反馈「侧滑返回逐章回退 / 搜索点了没反应 / 很多功能不能用」的一轮修复。核心是补上 Android WebView 的系统能力缺口。

| 问题 | 修复 |
|---|---|
| 侧滑返回逐章回退 | 章内跳转改 `history.replaceState` + 直接重渲染阅读器（`goChapter`），不再每章压一条历史；系统返回/侧滑直接退出阅读页回详情 |
| 破坏性操作在 APK 中静默失效 | 原生壳 `WebChromeClient` 未实现 `onJsConfirm` → `window.confirm` 恒 false。改用**自绘 Promise 确认弹层**（`confirmBox`），移出书架/删除书源/清空缓存·数据/删除分组/导入确认全部恢复 |
| 搜索"点了没反应" | 搜书框改为 `<form>` 提交（软键盘「搜索」键、回车、箭头三条路径统一），提交后收键盘并把结果滚入视野 |
| 导出书源/导出备份无反应 | WebView 不支持 `a.download`+Blob；新增原生 `ModouBridge.saveFile`（系统 SAF「另存为」，无需存储权限），前端 `saveFile()` 桥内走原生、浏览器回退下载 |
| 详情页无返回入口 | 详情页顶部加返回胶囊（`history.back()`，无历史则回书架） |
| 分页模式底部被工具坞遮挡 | `.page` 底部内边距扩到 ~80px，正文不再被悬浮工具坞盖住；顶部栏加同色渐变，滚动文字不再与书名/按钮重叠 |
| 箭头语义不清 | 分页模式下左右箭头=翻页（到章末自动进下一章），滚动模式=翻章 |
| 清空数据漏清书签 | 「清空所有数据」补上 `bookmarks` store |

## v0.6.17 修复 + 体验（代码审查专项：MD5 / 试读缓存 / 搜索页退出 / 自动阅读跨章 / 发现翻页 / 封面分色）

通读全部 web 源码 + Android 壳 + Node 代理后定位并修复的确定性问题：

| 问题 | 根因与修复 |
|---|---|
| 依赖 MD5 签名的书源全部失败 | `sandbox.js` 的 `simpleMd5` 是**伪造实现**（只算一轮 4 步、注释自认不完整），`java.md5`/`md5Encode`/`md5Encode16` 输出错误哈希。替换为**完整 RFC 1321 MD5**（4 轮 64 步、K 常数表 + 移位表 + 消息扩展、UTF-8 字节参与），已用 8 组已知向量校验（含中文多字节、`a×56` 跨块），并与 Node `crypto` 逐字节一致 |
| 试读「重新加载本章」清不掉缓存 | `previewChapterPut(index, null)` 用 `sessionStorage.setItem(key, null)` 把 `null` 存成字符串 `"null"`，重载后被当成缓存正文。改为 `null` 时 `removeItem` 真正清除；`loadPreviewCache` 顺手丢弃历史脏数据 `"null"` |
| 离开阅读页后再次打开「全书搜索结果页」history 错配 | `openFindPage` 推了 `history.pushState` 占位，但 `renderReader` 重渲染时没重置模块级 `fpPushed`，导致再次打开误判「已 push」、不再压入正确历史项。在 `renderReader` 入口重置 `fpPushed = false`（`#find-page`/`#find-bar` 本就在 `view` 内随路由抹掉，无需额外清理） |
| 自动阅读走到章末就停，不接着读下一章 | `paint` 每次重渲染都 `stopAuto`，跨章即死。改为：分页/滚动模式章末检测若有下一章，置 `gAutoContinue` 后 `goChapter` 续读、`renderReader` 在 `paint` 后重新 `startAuto`（正文加载失败则不再续）；仅**全书最后一章**才提示「已到全书末尾，自动停止」 |
| 发现页是半成品：只拉第 1 页、无翻页/加载态 | `explore` 本就支持分页参数。新增模块级 `exploreState`（换源自动重置、离开可恢复）：「浏览」拉第 1 页，「加载更多」续拉并去重累加，期间显示「加载中…」，到底显示「—— 已到底 ——」，非分页源无新内容即自动到底（防死循环） |
| 同名长度的书撞同色占位封面 | `coverImg` 用 `id.length` 当散列种子，熵太低易撞色。改为对 **id 字符串做 FNV-1a 散列**取色，同名不同书、同长不同书都能均匀分色 |
| 切到新章节后往回翻一页，会「刷地翻过十几页」的假腾跃动画 | 跨章落回上一章末页时，`paint` 先按阅读进度定位（可能在中段），随后 `showPage(pageEls.length - 1)` **没传 anim=false**，于是从中段**带动画**滑到末页。跨章落点改为一律无动画 |
| 缺页眉页脚设置 | 新增**页眉页脚**（排版面板 → 页眉页脚，仅分页模式）：页眉可选「不显示 / 章节名 / 书名」，页脚可勾选「页码 / 时间 / 电量」（默认章节名 + 页码）。页眉页脚高度在 `paginate` 里**实测后从可用正文高度扣除**，正文不会被盖住；总页数确定后再回填页码，时钟每 30s 刷新 |
| 开启页眉页脚后个别页末尾被裁掉 | 分页算法「本页放不下 → 换新页」后是**无条件整段塞入**，遇到比一整页还高的长段落就溢出（实测某页溢出 50px，被 `.page` 的 `overflow:hidden` 裁掉）。重构装页循环：换页后用整页高度重新量，能整段放就放，否则**按整页切一段**，切不动（图片/章题）才整段塞。修复后 15 页**最大溢出 0** |

## v0.6.96 插图改成「真的占几行」，不再靠 span 撑行高

> 前两版都在跟 `ImageSpan` / `ReplacementSpan` 的 `FontMetricsInt` 较劲，方向就是错的：
> 在 `StaticLayout` 的测量路径里，span 报的行高根本改不动这一行 —— 实测图照样溢出，
> 所以第三次不再猜，改用排版器一定会照做的事。

| 问题 | 根因 | 改法 |
|---|---|---|
| 插图仍然压住正文、顶到章标题下面 | span 方案（`ImageSpan` → `AbsoluteSizeSpan` → 自绘 `ReplacementSpan`）都试图通过 `getSize()` 改行高；但 `StaticLayout` 用的是**测得的字体度量**，span 报的高度不参与行高计算，图始终被塞进「一行字高」的盒子里，从基线往上溢出 | 插图不再挂 span：按「图高 ÷ 行高」算出要几行，**插入真正的换行**把这 k 行占满（占位字符用全角空格，看不见）；绘制时按 `layout.getLineForOffset` 找到它所在行，在这 k 行的矩形里居中把图画出来（`drawImgSlots`）。行高由排版器自己算，图不可能越界 |
| 分页时图被切成两半 | 分页只按「这一行放不放得下」推进，图的第二行可能被切到下一页 | 分页时遇到「插图起始行」，要求整块图都放得下才收进本页，否则本页到此为止 |
| 长图占满整屏、上下没有呼吸 | 图高上限是一屏的九成 | 收到八成，并在图块上下各留半行字 |

顺带把行距实现从 `setLineSpacing(0, multiplier)` 换成 `setLineSpacing(add, 1)`（行高总和不变、

## v0.6.84 修复启动白屏：全量迁移不再挡在首屏前面（P0）

> v0.6.82/0.6.83 引入了共享存储层，首次启动要把 IndexedDB 全量搬进 SQLite。这段搬迁被 `await` 在了 `boot()` 最前面——书架里缓存上千章正文时，界面几十秒不出内容，用户杀进程后下次启动**又从头搬、又白屏**，卡成死循环。

| 修复 | 说明 |
|---|---|
| 迁移移出首屏 | `initStore()` 只在「上次已迁完」时立刻切 SQLite（一次 SharedPreferences 读取，微秒级）；否则本次照旧走 IndexedDB **秒开**，迁移丢到后台空闲时慢慢搬，搬完**下次启动**才生效 |
| 游标分批 | 原来是「取全部 key → 逐条 get」，等于每条记录开一个 IndexedDB 事务，几千章就是几千次往返。改成每批一个游标事务，往返次数从「记录数」降到「批次数」，批间让出主线程 |
| 双写防丢 | 后台迁移完成后进入双写：本次仍读 IndexedDB，但新写入同步进 SQLite，否则切换时会丢掉这段时间的进度/书签/设置 |
| `boot()` 兜底 | async 的 `boot` 原先**没有任何 catch**，任何一步 reject 就静默白屏。现在初始化失败降级继续渲染（书架可能是空的，但界面在、可操作），渲染彻底失败则显示可见的错误卡片 + 重试按钮，而不是「什么都没有」 |
| `open()` 防挂起 | IndexedDB `blocked` 时既不 success 也不 error，Promise 会永远挂着。现在直接 reject，让上层走兜底 |

**验证**：新增回归锁定「首屏不被迁移阻塞」——800 章缓存下首屏 **46ms** 可见（修复前需等完整搬迁）；桥全部抛异常时界面仍渲染出书架（不再白屏）。存储层 44 条、ui-smoke 223 / reader-layout 122 / e2e 117 / local-import 35 / tts 21，全 0 失败。

## v0.6.42 跨章"卡一下"真因：跨章等于重开一次阅读器，改为原地切章

> 反馈：「跨章翻页还是会卡一下，而且是本地书籍，开源阅读没这个问题」——本地书排除了网络，所以问题在渲染链路。

**先量化，再改**：用 Playwright 造真实滑动，量「松手 → 动画真正开始」这段时间。

| | 改前 | 改后 |
|---|---|---|
| 跨章翻页 | **49ms**（峰值 65ms） | **31.2ms** |
| 章内普通翻页 | ~30ms | 30.1ms |
| 两者差值 | **~19ms 的"卡"** | **1ms（可视为持平）** |

| 根因 | 说明 | 修法 |
|---|---|---|
| **跨章 = 重新初始化整个阅读器** | 跨章走 `renderReader`：十几次 `await settings.get()`、全套事件绑定、工具坞/目录/TTS/唤醒锁重建……而滑入动画必须等这些**全部做完**才能开始。章内翻页只有一次 transform | 新增 **`switchChapterInPlace`**：跨章只做「换正文 → 重分页 → 滑入 → 存进度」，不重建阅读器（设置/绑定/面板全部复用） |

| `paginate` 的首帧延后判断失效 | v0.6.40 用 `gPendingSlide` 判断，但 `paint()` 在调用 paginate **之前**已把它清零——那段代码从来没生效过 | 改为显式参数 `paginate(restore, { deferFirstPaint })`，由调用方声明 |
| `fitChars` 二分探测 | 每段 setTextContent + 读 offsetHeight 都是强制重排，300 字要 9 次；一章几十次切分就是数百次重排 | 用「整段高度 / 行高 = 行数」反推每行字数，一次估算 + 最多 3 次修正；重排从 ~9 降到 ~2（顺带让首次打开、改字号也更快） |

|---|---|

## v0.6.20 修复 + 体验（关掉网页式缩放）

> 反馈：「你这软件做的跟浏览器看到的网页一样，可以随意的放大缩小，你觉得合理吗」。根因：WebView 默认允许双指/双击缩放，viewport 也没锁——App 壳从来没收紧过。

| 模块 | 内容 |
|---|---|
| 缩放开关 | 原生三层全关：`setSupportZoom(false)` + `setBuiltInZoomControls(false)` + `setDisplayZoomControls(false)`；viewport 加 `maximum-scale=1.0, minimum-scale=1.0, user-scalable=no`（与原生双保险） |
| 顺手去网页感 | `setOverScrollMode(OVER_SCROLL_NEVER)`——滚到边缘的蓝色荧光（overscroll glow）也是"这是网页"的强信号，一并去掉 |

## 架构

```
┌──────────────────────────────────────────────┐
│ Java/原生壳（android/，已交付 APK）              │
│   WebView 容器 · 本地 HTTP 服务 · TTS/分享桥     │
├──────────────────────────────────────────────┤
│ WebView 壳 + HTML/JS SPA（web/）               │
│   ├─ ui/        书架/搜书/详情/阅读/书源管理/设置 │
│   ├─ lib/       本地导入：txt/zip/epub 解析      │
│   ├─ engine/    规则引擎（见下）                 │
│   ├─ http.js    统一走本地代理                 │
│   └─ db.js      IndexedDB（书源/书架/进度/缓存） │
├──────────────────────────────────────────────┤
│ 本地代理层（双实现，行为一致）                    │
│   server/proxy-server.js   Node dev server     │
│   android/ LocalServer      APK 内 NanoHTTPD   │
│   /proxy 转发 · UA/Header 注入 · GBK 编码归一   │
│   MODOU_FIXTURES=1 时回放 test/fixtures        │
└──────────────────────────────────────────────┘
```

Android 壳（`android/`）不承载任何业务逻辑：`MainActivity` 起本地服务后把 WebView 指向
`http://127.0.0.1:39617/`，前端 `location.origin` 自动正确——**浏览器开发和 App 里跑的是同一份代码、
同一条 /proxy 通道**。壳只提供系统能力：`<input type=file>` 文件选择器（书源 JSON / TXT / EPUB，
按 accept 属性映射 MIME）、VIEW intent 书源 JSON 导入、Android TTS 朗读（`window.ModouBridge`，
浏览器侧自动回退 Web Speech）、系统分享。构建见 `android/README.md`。

引擎四件套（`web/js/engine/`）：

| 文件 | 职责 |
|---|---|
| `rule.js` | 规则求值：CSS/XPath/JSONPath/正则/JS、`&&` 链式、`##` 净化、`#` 分割、`-` 倒序 |
| `jsonpath.js` | JSONPath 子集（`$.a[*].b`、`..key`、切片、`[?()]` 过滤） |
| `sandbox.js` | `@js:` 规则执行环境 + `java.*` 桥（http/base64/md5/log/src 变量） |
| `source.js` | `BookSource` 类：search / explore / bookInfo / toc / content 全链路 |

本地导入三件套（`web/js/lib/`）：

| 文件 | 职责 |
|---|---|
| `txt.js` | 编码探测（BOM/UTF-8 严格/GBK 回退）+ 智能分章 + 文件名书名作者试探 |
| `zip.js` | 最小 ZIP 读取器（中央目录 + deflate-raw 解压） |

### 1. 分页末行只显示几个字，大半行留到下一页（已修：v0.6.45）

现象：一屏文字的最后一行常常只有三五个字（截图里是「当，可这野」），本该接着写的内容整体被推到下一页，
视觉上像一行被硬折断，页面底部利用率很低。

初步定位（已读代码确认）：`reader.js` 的 `fitChars()` 先用「整段高度 ÷ 行高 = 行数」反推
`perLine = 字数 / 行数`，再用 `Math.floor(maxH / lineH) * perLine` 估一个字数 `guess`；
估少时**只按整行步长 `step = ceil(perLine)` 往上跳**，跳一档就超高、于是 `break`，末行就这样停在半截。
因为 DOM 高度对末行文案是**阶梯函数**（末行多加几个字高度不变），用整行步长去逼近必然跨过台阶。

修复方向：
- `fitChars()` 末行改为**区间二分**：在 `[guess, guess + step]` 内二分逼近，判据用
  `probeEl.offsetHeight <= maxH`（高度没跳档就继续加字），约 5 次即可把末行填到 95% 以上；
- 或更精确地判「末行是否还有空位」：`probeEl.getClientRects().length` 取行数 + 末行宽度，直接算还能塞几个字；
- 两种都只增加 3~5 次探针重排（probe 在隐藏测量容器里），对跨章翻页耗时影响可忽略；
- 验收：连续翻 30 章统计末行宽度利用率（应 ≥ 60%），且页面不能因此少行（底部出现大片空白同样算失败）。
- 注意：改这里必须回归预分页（`primeChapter`）、跨章翻页（`applyChapter`）、目录跳章——它们共用 `paginate()`/`fitChars()`。

### 2. 夜间模式不全局：只在阅读页生效，退出后仍是亮色（已修：v0.6.45，v0.6.46 补开屏不闪）

现象：阅读页点「夜间」变暗，返回书架 / 书源 / 设置还是纸白亮色，观感割裂。
用户预期：阅读页开夜间 = 整个 App 夜间。

定位（已确认）：`web/styles.css:17` 有完整的 `[data-theme="dark"]` 变量集，但**从来没有被启用过**；
JS 只在 `document.body` 上挂 `data-reader-theme="dark"`（样式域仅限阅读页），
`index.html` 写死 `<html data-theme="light">`。

修复方向：
- 引入全局主题状态（`settings` 键如 `appTheme` = `light | dark | auto`），启动时写 `documentElement.dataset.theme`；
- 阅读页切「夜间」时**同步**写全局主题；阅读页的「纸白 / 米黄 / 青石」仅决定阅读区底纸色，不反向改全局；
- 设置页补「跟随系统 / 浅色 / 深色」三选，`auto` 用 `matchMedia('(prefers-color-scheme: dark)')` 并监听变化；
- 现有 `[data-theme="dark"]` 是 M3 时期留下的，变量覆盖不全，需逐个补齐：书架卡片、底部导航、抽屉、浮层/遮罩、
  输入框、分段控件、书源卡片、阅读页工具坞、系统栏（`--bg` 之外的硬编码白色/浅色阴影要一起清）；
- 验收：夜间与日间各截 6 屏（书架 / 详情 / 阅读 / 目录 / 书源 / 设置），不允许残留白底黑字区块。

### 3. 翻页时菜单（顶部栏 / 底部工具坞）不自动收起（已修：v0.6.45）

现象：点正文中部唤出工具栏后，再做翻页手势 / 点左右分区翻页，菜单仍停在屏幕上，不进入沉浸态。
预期：任何主动翻页动作都应自动收起 chrome（与「点文字中部才显隐」一致）。

定位（已确认）：`toggleChrome()` 只在点「中部」时切换 `view.chrome-hidden`；`turnPage()` / `bindPaging` 的翻页分支
成功翻页后**没有**补 `view.classList.add('chrome-hidden')`，所以菜单会一直挂住。

修复方向：
- 在 `turnPage()` 真正翻页成功的分支（章内 `showPage(ni)` 前、跨章 `goChapter`/`switchChapterInPlace` 前）收起 chrome；
- 翻页手势 `onUp` 里 `dist > threshold` 或 `flick` 命中翻页时也收起（同样走 turnPage 即可统一）；
- 边界不翻（书首尾）不收（维持现状）；
- 滚动模式（`!paged`）下 stage 滚动本就 `hideSelBar`，顺带收 chrome 也合理（沉浸阅读）。

### 4. 选中文字「选多一点」就稳定触发阅读页错乱（多页并排 / 半行裁切 / 竖条残片）（已修：v0.6.45）

现象：长按划选文字，选中范围一多（跨多行、尤其接近跨页），正文区就整体错位——能同时看到 2~3 页的碎片，
文字被挤成窄列、左右出现竖条残片，只有退出重进阅读才恢复。

定位（已确认，根因在布局而非选区本身）：
`.page` 用 `position:absolute; width:100%; left: i*100%`（`reader.js:903`），其 `left` 百分比会**撑大** `.rd-stage`
的 `scrollWidth`（`.rd-stage` 在分页模式下 `overflow:hidden` 但仍可被**程序滚动**）；
选区跨页时 WebView 为了让选区末端进入视口，对最近的可滚祖先执行 `scrollIntoView`，
把 `.rd-stage.scrollLeft` 改掉 → 整屏横向平移，于是看到相邻页的横向碎片。这跟「选多少」正相关，
因为选区越大越容易跨页、越触发滚动。

修复方向（根治 + 兜底，两者都做）：
- **根治**：`.page` 改用 `transform: translateX(i*100%)` 而非 `left:i*100%`（transform 不参与滚动区域计算，
  `scrollWidth` 恒等于视口宽，浏览器无从横向滚动）。对应改 `reader.js:903` 与 CSS `.page{left:0}`；
- **兜底**：给 `.rd-stage`（分页模式下）加 `scroll` 监听，若 `scrollLeft/scrollTop` 非零立即归零，
  防任何残留/其它路径触发的偏移；
- 注意：`.pg-slot` 加载页（`reader.js:2382` `loadPg.style.left='0%'`）一并核对；`slideIn` 的 ghost 用 transform，不受影响。
- 验收：连续选满屏、跨页选、选到接近页尾各 5 次，正文区不得出现横向偏移（用 `rd-stage.scrollLeft` 断言为 0）。

### 5. 书源页 UI 重做（统筹重设计，排在以上功能 bug 之后）（已修：v0.6.47）

- **v0.6.129** 书多了以后书架卡死/整机变慢的根因是**书架把每本书的完整记录都读了一遍**（每本带几千项章节表 + 内联 base64 封面，三十多本十几 MB，冷启动快照还把这份数据写进了 SharedPreferences 在主线程解析）。改为：`books` 表加 `lite` 列，写入时只存书架要用的字段（含 `chapterCount`），书架只读 lite；内联封面落盘到 `files/covers/`（`CoverLoader` 支持 `file://`）；旧书后台分批回填（1.2 秒一轮，封面陆续出现）；超 200KB 的老快照直接丢弃；改分组/收藏/编辑信息写回时先合并库里的完整记录，不会再把章节表抹掉；网页侧 `reloadBooks` 改走轻量接口，`findBook` 按 id 补全章节。顺带停掉「本地书自动在线搜封面」——本地书没有书源，三十多本会变成三十多次网络搜索，后台一直忙（一次最多补 8 本，单本超时 25s→12s）。
- **v0.6.130** 书架从阅读页返回后跳回顶部：`reload → paintPane` 整页重建，新 ScrollView 位置是 0。现在重建前记下滚动位置，同一视图（tab/分组/排序都没变）重绘后放回去（阅读历史、收藏同样是列表，一并处理）。「最近阅读」排序重启后变回原样：阅读时只写 `progress.updatedAt`，progress 里查不到这本（老数据无 bookId、本地书 id 变化）排序就退回加入时间；现在每次存进度同时用一条轻量 `UPDATE` 更新 `books.updatedAt`（只改列和几百字节的 lite，不碰章节表），书架读 lite 时以列为准；排序偏好除 settings 再存一份 SharedPreferences 兜底；写回书籍记录时不把 `updatedAt` 倒拨，避免冷启动快照的旧值覆盖刚读的时间。
- **v0.6.131** 打开书慢/换章慢按成熟阅读器的做法重做数据通路：① **入口只传 `bookId + index + offset`**，不再把整份目录（`titles[]`）和本章正文塞进 Intent —— 三千章的书那个 payload 是 243KB、六千章 392KB，跨进程传输本身要几百毫秒，逼近 Binder 的 1MB 上限就会 `TransactionTooLargeException`，表现正是「点了封面半天打不开，然后自己退回书架」；② 正文与目录全部在后台线程取（读库 → 净化规则 → HTML 切块），主线程只排版一次，不再在点击/翻页时做几十 KB 文本的正则与解析；③ 加**下一章预取**与 4 章 LRU 块缓存，翻章命中内存，只剩排版；④ `ModouStore.chapterCount()` 只读 `lite.chapterCount`（缺失才回落 json），入口不必为了「一共几章」解析整份目录。
- **v0.6.132** 排版对齐 + 打开详情不再卡：① **整字数排版**——中文一格 88px、版面 1272px，一行排 14 字只用掉 1232px，剩下 40px 全堆在右边（右边距比左边大近半个字、每行末尾空小半格）。现在正文宽度取整字、余量对半分到左右留白（`applyCellGrid`），左右留白相等、右边界齐；② **标点挤压**——全角标点的墨迹只占格子左半，行尾落在“，。”“。”上就空出半格，这也是「右边不齐」的主因。改成半格占位（`HalfPunctSpan`，与开源阅读 legado 的 ZhLayout 同一思路），字符数不变（选区/书签/进度偏移不受影响），一行能多容一个字；③ 详情页改**轻量记录先出界面**（`ModouStore.bookLite`），完整记录（几千章目录 + 内联封面）后台读回来只补目录卡片，不再在主线程 `new JSONObject` 几 MB；写回一律先合并完整记录，避免把目录写没；④ 阅读页「没有缓存章节」时向书源取章的那条路，把 `bookObj()` 从主线程挪到后台（本地书以前还要白解析一遍整本记录才退出）；取回来的正文净化/切块/写缓存也在后台；⑤ 目录后台补齐后补上章标题（瘦入口进来时标题是空的，得翻页才出现）。
- **v0.6.133** 冷启动与首次进书专项，排版按开源阅读的手感再收一档：① **冷启动不再建 WebView**——以前书架盖上来（`onStop`）就顺手 `new WebView`，Chromium 初始化是主线程 1~3 秒的活，用户紧接着点开一本书，进书与排版全排在它后面，表现就是「冷启动后第一本书究极慢、第二本又正常」。现在引擎只在真需要时创建（迁移旧数据 / 刷新目录 / 缓存全书 / 书源兜底，`MainActivity.ensureBridge()`），纯本地阅读一个字节的 WebView 代码都不跑；② **设置表内存快照**——进书要读十几个设置项，以前每项一次 SELECT，冷启动数据库还没热起来就串成几百毫秒。改为启动时后台 `preloadSettings()` 整表读进内存，写设置同步更新（含 JS 经桥写入），读设置不再碰数据库；③ **后三页懒加载**——书源/规则/设置三页的读库与控件构建推迟到第一次滑到，书架首帧不再替它们买单；④ **后台杂活让路**——`ensureBookLite` 只把「取一条待补记录」放进锁里（解析 json、写封面文件在锁外），阅读页在前台时直接暂停回填；自动补封面从「书架一画完就搜」改成 6 秒后、且不在看书时做（它会拉起无头 WebView）；⑤ **换章只排一次版**——以前 `setChapter` 排一遍、`setTitle` 又整章重排一遍，一章两万字等于白排一次 `StaticLayout`；合并成 `setChapter(body,title,offset)` / `setBlocks(blocks,title,offset)`；⑥ **页边距默认 24→16dp**（滑杆 8–36），并且不再用「余量对半分到左右留白」——那等于把两边留白都悄悄撑大半格。改成把不足一格的余量平摊到字距（`letterSpacing`，每字约 2~3px），左右留白严格等于设定值、右边界齐平，观感与开源阅读一致。
- **v0.6.134** 「下一章死活加载不出来」专项（冷启动后从书架中后段打开的书最明显）：① **书架不再在阅读时抢库**——书架原先没有 `onPause`，`reload()` 里还挂着「每 600ms 再来一轮」的自循环，读者翻章时后台仍在补 lite、整表读 books、重建整页书架，两边抢同一把数据库锁和同一条主线程；阅读页又会把 `ensureBookLite` 直接短路成「返回待补数」，于是这个循环在看书期间**永不停止**。现在书架被盖住（`onPause`）就彻底收手，`reload()` 只读不补；lite 回填挪到单独的 `modou-lite` 线程，只补不读、补完才刷一次书架；② **索引**——`books(lite)` 与 `books(id,name,author,grp,kind,addedAt,updatedAt,lite)` 两个索引：前者让「找还没补 lite 的书」不再逐行读整条记录（一条就是几 MB 的 json + 几百章目录），后者是覆盖索引，书架刷新只扫索引、与 json 大小解耦；③ **换章请求可被顶掉**——原先 `if (loadingChapter) return;` 会把卡住之后的所有点击静默吃掉，现在用代次（`chapterGen`）让新请求顶掉旧请求，旧回调回来发现自己过期就丢弃；④ **每条路径都有超时**——「读库」那条以前没有超时，卡在等锁上就是永久转圈；现在读库/书源/网页桥统一 12 秒，超时作废该代次并提示「再点一次」；书源超时从 32 秒收到 12 秒；⑤ **章数守卫不再静默 return**——书架带下来的 `chapterCount` 落后于真实目录时，以前点「下一章」什么都不发生；现在以库里目录为准刷新 `total`，真到头才提示「已经是最后一章了」；⑥ **预取与目录解析换到独立线程**（`modou-bg`）——它们原先和「用户正等的这一章」挤在同一个单线程池，预取一本大书就能把下一章堵在后面；⑦ **网页桥兜底只在网页入口生效**——原生书架进来没有 `session`，`__modouNativeChapter` 收到调用只会直接返回，白等一个超时；现在按 `fromNative` 直接给出结论「这本书没有可用的书源规则」，不再转圈。
- **v0.6.135** 三处硬伤：**大章读不出来 / 导入慢 / 书源导入无反应**。① **换章提示「这一章没有正文」的真因**——不是导入坏了，是**读取**撞上了 Android 的 CursorWindow 单行 2MB 上限：EPUB 插图被内联成 base64 写进章节 HTML，一张 3~4MB 的图就让一行到 5MB，`SELECT content` 直接抛 `Row too big to fit into CursorWindow`，旧代码把它吞成 null，上层只能报「没有正文」——所以重新导入多少次都一样，别的软件却正常。现在先 `length()` 量长度、小字段一次取、大字段按 12 万字用 `substr` 分片拼回（`readTextByKey`），桥上的 `get("chapters", …)` 也走同一条路；② **导入慢**——插图改为**落文件**（`EpubBook.ImageSink` → `files/epub/<书指纹>/`），章节里只留 `file://` 地址：实测一本 1200 章、每章一张插图的合集，正文从 **97.9MB** 降到 **1.98MB**，解析 1.05s → 0.70s，写库量少了 50 倍，导入不再一行行走半天；③ **导入完整性校验**——`putChapters` 事务回滚时以前仍按「已写入」计数，于是一本章录齐全、正文缺段的书照样报「已导入」；现在如实归零，导入侧比对实写章数，不够就提示「只写入了 X/Y 章：存储空间可能不够」并回滚，不再产出一本点进去全是空白的书；④ **书源导入**——解析 JSON 与逐条写库挪到后台线程（上百个源的合集在主线程上是十几秒卡死，用户看到的就是「点了没反应」），输入框补上宽高（以前缩成一条细缝），并给全四种结果提示：已导入 N 个 / 没有可导入的（缺地址）/ 不是合法 JSON / 面板打不开。
- **v0.6.136** 书源「导入」点了没反应：① **根因是关面板后 post 的消息丢了**——点击处理写的是 `self.dismiss()` 之后 `v.postDelayed(this::showImport, 120)`，而 `v` 就是面板里那个按钮，`dismiss()` 之后它已经从窗口上摘下（`mAttachInfo` 为 null），此时 post 出去的 runnable 只进 `ViewRootImpl` 的 RunQueue，要等 View 重新 attach 才执行——它永远不会再 attach，于是「点了导入什么都不发生」（同一处的「检查重复」也中招）；改挂主线程 Handler（`later()`），与 View 的 attach 状态无关；② **支持从本地文件导入书源**——「⋯」里拆成两项：「从文件导入（.json / .txt）」走系统文件选择器（`ACTION_OPEN_DOCUMENT`，MIME 同时登记 json / text / octet-stream，各家的标注不一样），「粘贴书源 JSON」保留原来的文本框入口；读取在后台线程、忽略文件头 UTF-8 BOM（不少导出工具会写 BOM，直接 `new JSONObject` 就报「不是合法 JSON」，用户完全看不出原因），读到的内容交给原有的 `doImport`（解析 + 写库也在后台）；③ **书架补上 `onActivityResult` 转发**——书源页与设置页是嵌在 `HomePager` 里的 View，没有自己的 Activity，书架又从未实现这个方法，所以选完文件回来没人接：书源导入、设置里的「导入备份」都会停在「点了没反应」。现在转发给两个面板。
